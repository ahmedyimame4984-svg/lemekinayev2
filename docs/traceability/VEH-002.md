# VEH-002 — Vehicle Master configuration foundation

## Scope

This increment expands the first Make/Model vehicle baseline into the canonical
Vehicle Master required by the Lemekinaye Master Developer System
Specification.

The canonical structure is:

```text
Vehicle Make
  → Vehicle Model
    → Vehicle Generation
      → Vehicle Trim / Variant
        → Vehicle Configuration
             ↳ Engine Master
             ↳ Transmission Master
             ↳ Body Type Master
             ↳ Market Master
             ↳ Model Year / Production Period
             ↳ Steering Side
```

Engine and Transmission are independent master-data entities. They are not
parent/child records. `VehicleConfiguration` is the join point that identifies
a concrete or partially resolved vehicle variant.

## Source alignment

Document 03 requires a structured vehicle master covering Make, Model,
Generation, Year, Trim/Variant, Engine, Transmission, Body Type and Market.

Document 04 requires one canonical Vehicle Master and explicitly states that not
every resolved vehicle record must contain every level. The implementation
therefore requires Make + Model while allowing Generation, Trim, Engine,
Transmission, Body Type, Market, Year and Steering Side to remain nullable when
source data is incomplete.

The Master Data Dictionary's canonical Vehicle entity similarly references Make
and Model mandatorily and the deeper configuration dimensions conditionally.

## Data model

New normalized master entities:

- `VehicleGeneration`
- `VehicleTrim`
- `VehicleEngine`
- `VehicleTransmission`
- `VehicleBodyType`
- `VehicleMarket`
- `VehicleConfiguration`

### Generation

A Generation belongs to one Vehicle Model and may carry:

- canonical/internal code
- display name
- production start year
- production end year
- lifecycle status
- optimistic version

### Trim / Variant

A Trim belongs to one Generation and may carry:

- trim code
- canonical trim name
- equipment level
- production start/end year
- lifecycle status
- optimistic version

Engine and Transmission are deliberately not stored directly on the Trim row.
Different engine/transmission combinations of the same Trim are represented as
separate Vehicle Configurations.

### Engine Master

Engine records may carry:

- manufacturer engine code
- canonical name
- engine family
- displacement in cc
- fuel type
- cylinder count
- aspiration
- normalized power in kW
- normalized torque in Nm
- production range
- lifecycle/version metadata

### Transmission Master

Transmission records may carry:

- manufacturer code
- canonical transmission type
- gear count
- drive type
- production range
- lifecycle/version metadata

### Body Type and Market

Body Type and Market are independently governed master data so market variants
are not incorrectly represented as separate Vehicle Models.

### Vehicle Configuration

A configuration stores:

- canonical configuration code
- Make ID
- Model ID
- optional Generation ID
- optional Trim ID
- optional Engine ID
- optional Transmission ID
- optional Body Type ID
- optional Market ID
- optional model year
- optional production start/end years
- optional steering side (LHD/RHD)
- lifecycle status
- optimistic version

Make and Model are immutable configuration parents after creation. Deeper
configuration references can be corrected through versioned Admin updates.

## Integrity rules

The backend enforces:

- Model must belong to the selected Make.
- Generation must belong to the selected Model.
- A Trim requires a Generation.
- Trim must belong to the selected Generation.
- Trim production range must fit within the Generation range when both sides
  are known.
- Model year must fall within known Generation and Trim ranges.
- ACTIVE configurations require all referenced master records to be ACTIVE.
- ACTIVE Trims require an ACTIVE Generation.
- ACTIVE Generations require an ACTIVE Model.
- Active dependent configurations block deactivation of Engine, Transmission,
  Body Type or Market.
- Active Trims/Configurations block Generation deactivation.
- Active Configurations block Trim deactivation.
- Active Generations/Configurations block Model deactivation.
- Production start year cannot exceed production end year.
- All writes use serializable transactions, optimistic versions and audit logs.

## Public API

Public endpoints expose ACTIVE master data only:

- `GET /api/v1/vehicles/generations?modelId={id}`
- `GET /api/v1/vehicles/trims?generationId={id}`
- `GET /api/v1/vehicles/engines`
- `GET /api/v1/vehicles/transmissions`
- `GET /api/v1/vehicles/body-types`
- `GET /api/v1/vehicles/markets`
- `GET /api/v1/vehicles/configurations?modelId={id}&...`

The configuration endpoint supports optional precision filters for Generation,
Trim, Engine, Transmission, Body Type, Market, Model Year and Steering Side.

## Admin API

All mutation and administrative-list routes require active `ADMIN` plus
`vehicle.manage`.

Each new master supports list/create/update routes beneath:

`/api/v1/admin/vehicles`

Canonical codes are immutable after creation where a code exists.

## Example

```text
Toyota
└── Corolla
    └── E140
        └── GLI
            ├── Configuration A
            │   ├── Engine: 2ZR-FE
            │   └── Transmission: Manual
            └── Configuration B
                ├── Engine: 2ZR-FE
                └── Transmission: Automatic
```

The two configurations share the same Make, Model, Generation, Trim and Engine
while differing by Transmission.

## Deferred scope

This increment does not yet implement:

- Product-to-Vehicle Fitment / Compatibility records
- fitment exactness/range/conditional semantics
- fitment source and verification state
- compatibility conflict resolution
- VIN decoding/provider abstraction
- VIN-to-Vehicle resolution
- customer saved Vehicle Profiles
- chassis/frame identification
- bulk vehicle-data import
- duplicate vehicle merge/reconciliation

Those layers should reference the canonical Vehicle Master rather than create a
second vehicle hierarchy.
