# IAM-002 - Privileged Admin provisioning and MFA authentication

## Scope

IAM-002 delivers the backend security path required before the visual Admin Portal:
controlled platform-Admin provisioning, one-time activation, password plus TOTP
authentication, MFA-backed sessions, rotating refresh tokens, logout/revocation,
rate limiting, account lockout and authentication audit evidence.

The initial Admin is provisioned by an offline operator command. There is no public
Admin-registration or role-assignment endpoint. Once authenticated with MFA, an
Admin holding `admin.accounts.manage` can provision another platform Admin through
the protected API.

## API contracts

| Method | Route                                | Authorization                                            | Result                                                                             |
| ------ | ------------------------------------ | -------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `POST` | `/api/v1/admin/auth/activate`        | One-time activation token                                | Sets the password and returns a short-lived MFA enrollment challenge and TOTP seed |
| `POST` | `/api/v1/admin/auth/activate/verify` | Enrollment challenge plus TOTP                           | Activates the provisioned Admin; returns `204`                                     |
| `POST` | `/api/v1/admin/auth/login`           | Admin email and password                                 | Returns only a short-lived MFA challenge                                           |
| `POST` | `/api/v1/admin/auth/mfa/verify`      | Login challenge plus TOTP                                | Returns an access token and rotating refresh token                                 |
| `POST` | `/api/v1/admin/auth/refresh`         | Current refresh token                                    | Atomically invalidates both old credentials and returns replacements               |
| `POST` | `/api/v1/admin/auth/logout`          | Current refresh token                                    | Revokes the matching session; returns `204`                                        |
| `POST` | `/api/v1/admin/accounts/provision`   | MFA-backed `ADMIN` session plus `admin.accounts.manage`  | Creates or restarts a `PROVISIONED` platform Admin and returns a token once        |
| `GET`  | `/api/v1/admin/me`                   | MFA-backed Admin access token plus `admin.portal.access` | Resolves the current Admin roles and permissions                                   |

All public authentication endpoints are explicitly marked public only to the global
session guard; they apply their own token, credential, account-state, rate-limit and
attempt checks. They never accept a requested role or permission from the caller.

## Cryptographic and token controls

- Passwords use Node's `scrypt` with a unique 128-bit salt, `N=32768`, `r=8`,
  `p=1` and a 512-bit derived key. The encoded verifier is stored; the password is
  not.
- TOTP follows RFC 6238 with a random 160-bit seed, HMAC-SHA-1, six digits and a
  30-second step. Verification permits one adjacent step for clock drift and stores
  the last accepted counter so a successful code cannot be replayed.
- TOTP seeds are encrypted with AES-256-GCM and authenticated context. The required
  `AUTH_MFA_ENCRYPTION_KEY` must be a canonical base64-encoded 32-byte value.
- Purpose-specific MFA-encryption and source-hash keys are derived from that runtime
  master key with HKDF-SHA-256; the same derived key is not reused across controls.
- Activation, challenge, access and refresh credentials are generated from 256 bits
  of cryptographic randomness. Only SHA-256 hashes are stored.
- Responses that contain provisioning, enrollment, challenge or session credentials
  set `Cache-Control: no-store` and `Pragma: no-cache`.
- Admin access defaults to 30 minutes. The refresh credential rotates on every use
  without extending the default eight-hour absolute session expiry. Rotation also
  invalidates the previous access token.
- Source addresses are protected with a server-keyed hash before throttle or audit
  storage. User-agent values are length-limited session metadata; no password, TOTP,
  MFA seed or raw token is logged.

## Provisioning operations

Configure `.env`, apply migrations, and provision the first platform Admin:

```sh
openssl rand -base64 32
npm run db:migrate
npm run admin:provision -- --email admin@example.com --name "Platform Admin"
```

Place the generated key in `AUTH_MFA_ENCRYPTION_KEY` before running the command.
The printed activation token is sensitive, expires by default after 24 hours and is
shown only because the operator must deliver it out of band. Re-running the command
is allowed only while that Admin remains `PROVISIONED`; it invalidates earlier
provisioning and enrollment state. Active, suspended or deactivated accounts cannot
be silently reprovisioned.

## Database evidence

Migration `20260923200000_admin_mfa_auth` adds:

- encrypted Admin credential and enrollment state;
- hash-only provisioning and MFA challenge records with expiration, consumption and
  attempt counters;
- database-backed authentication throttle buckets;
- rotating refresh-token hashes, MFA assurance, source hash and user-agent metadata
  on sessions; and
- constraints and indexes for non-negative attempts, challenge shape, expiration
  queries and credential lookup.

A fresh embedded PostgreSQL run applied all four migrations and inserted the new
credential, provisioning, challenge and throttle records. A second database-backed
smoke completed provisioning, activation, password verification, TOTP verification,
RBAC resolution, refresh rotation and logout. It finished with the Admin `ACTIVE`,
MFA enrolled, seven audit events and the issued session revoked.

## Deferred requirements

The following remain incomplete and must not be represented as delivered:

- The visual Admin Portal login, enrollment and category/vehicle screens.
- Admin recovery, password reset, MFA reset, backup codes and privileged recovery
  approval procedures.
- Phishing-resistant WebAuthn/security-key factors and selectable MFA methods.
- Configured step-up challenges for individual high-risk actions beyond the current
  MFA-backed Admin session.
- Admin session-management UI, security notifications, alert routing and operational
  dashboards.
- Customer phone OTP and seller/business authentication and approval flows.

Deployment must terminate TLS before these routes, keep the encryption key in the
environment's secret manager, and configure proxy/IP handling deliberately at the
edge. Client token-storage design belongs to the Admin Portal milestone and must not
place sensitive tokens in insecure browser storage.
